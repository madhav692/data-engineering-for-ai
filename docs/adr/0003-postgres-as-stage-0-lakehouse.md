# ADR-0003: Postgres stands in for the lakehouse at Stage 0

- **Status:** Accepted
- **Date:** 2026-10-04
- **Deciders:** series author
- **Scope:** `platform/` at the `stage-0` tag; the fourth generator target in `packages/schemas/`

## Context

Stage 0 (A3) is a walking skeleton: every one of the seven subsystems present, each as thin
as its contracts allow, running from one Docker Compose file on a 16 GB laptop with the first
answer under ten minutes from a clean clone. ADR-0001 names Iceberg as the lakehouse. An
Iceberg lakehouse needs a catalog and a query engine in front of the first answer: on Compose
that is at least three more containers (catalog, engine, and a metastore or its database),
two more images to pull, and a second query dialect in the code before a single document is
ingested. The small dataset tier is about 300 documents and a few thousand chunks, which no
lakehouse feature (snapshots, time travel, partition pruning) earns its keep on.

The skeleton also needs a vector index. pgvector gives a cosine HNSW index inside the same
database, which keeps Stage 0 at three containers.

## Options considered

### A. Iceberg from day one (an S3 store + a REST catalog + Spark or Trino)

- **Fits:** no later migration of the lakehouse; the Iceberg DDL generator is used at once.
- **Loses:** three more containers and several GB of images before the first answer; a query
  engine in the request path or a second code path for serving; the article becomes about the
  lakehouse, which is A6's subject, not the skeleton's.
- **Would win when:** the stage's corpus needs snapshots or time travel to make its argument.
  That is Stage 1.

### B. SQLite plus a vector library (no Postgres at all)

- **Fits:** zero containers for storage.
- **Loses:** no `ON CONFLICT` semantics worth teaching, no concurrent writers, no path from
  Stage 0 to the hot request log the series needs in Postgres anyway (A4); the vector index
  would be an in-process library with no table to inspect.
- **Would win when:** the target were a single-user desktop tool.

### C. Postgres for the seven contract tables, pgvector for the index, an S3 store for raw bytes (chosen)

- **Fits:** one database, three containers in total; the seven contract tables are created from
  DDL generated by a fourth generator (`generate/postgres.py`) from the same models that
  produce the Iceberg DDL, so a field added to a model shows up in both targets in one diff;
  `ON CONFLICT` expresses the idempotency keys the contracts name; the index is a separate
  table built from the lakehouse tables by a job that records what it read, so the seam
  between subsystems 2 and 4 is real; raw bytes already live behind an S3 API, so Stage 1's
  Iceberg tables land beside them without a migration.
- **Loses:** no snapshots: `lakehouse_snapshot_id` is the time of the newest embedding the
  build read rather than an Iceberg snapshot id; no time travel; the lakehouse copy of a
  vector is `REAL[]`, never searched, only rebuilt from; a second database dialect
  (Postgres) exists beside the Iceberg one.

## Decision

Option C. At Stage 0:

- `cairn migrate` applies `packages/schemas/generated/postgres/*.sql` in lineage-spine order,
  then the platform's own non-contract DDL (`latest_documents` view, the feedback dedup
  unique index, supporting indexes). Index tables are not contract tables; the index
  subsystem creates one per index name (`idx_<index name slug>`) with `vector(dims)` and an
  HNSW index, and `index_snapshots.status = 'live'` is the pointer retrieval follows.
- `lakehouse_snapshot_id` is `max(embeddings.created_at)` for the model at build time,
  rendered as an ISO-8601 string. At Stage 1 it becomes an Iceberg snapshot id and nothing
  else in the `IndexSnapshot` contract changes.
- Type mapping for the fourth generator: TEXT, BIGINT, DOUBLE PRECISION, BOOLEAN,
  TIMESTAMPTZ; TEXT[] for string arrays; JSONB for maps, nested records and other arrays;
  TEXT with a CHECK for enums; a real PRIMARY KEY; per-field `postgres_type` overrides
  (the vector column is `REAL[]`). Iceberg partition specs are recorded as a comment and not
  applied.

## Consequences

**Positive**

- Three containers, two image pulls, first answer well inside the ten-minute budget.
- Contracts C1 and C3 are exercised against a real database with real conflict semantics.
- The seam to the index (C4) is a job that reads lakehouse tables and writes an
  `IndexSnapshot`, which is exactly the shape it keeps when Qdrant replaces pgvector.

**Negative**

- Stage 1 (A6) replaces the storage behind C1 and C3 with Iceberg and must prove that neither
  contract changed; that migration is the seam test A2 promised, and it is on the plan, not
  avoided.
- Index lag is computed from `source_updated_at`/`fetched_at` against `built_at`, not from
  snapshot ids; the number is the same, the provenance is weaker until Stage 1.
- Threshold to revisit: the moment a stage needs snapshot isolation between a build and
  concurrent ingests, or time travel for an audit, Postgres stops being enough.

## Note on the object store

The S3-compatible store in the `core` profile is SeaweedFS (`chrislusf/seaweedfs`), not MinIO.
MinIO's community Docker images stopped being published in October 2025 and the project was
archived in 2026, which would have put a dead image in front of `make start`. Nothing in the
platform depends on the product: the code speaks the S3 API through the `minio` client library,
and any S3 endpoint (SeaweedFS, AWS, Ceph RGW, Garage) satisfies it. SeaweedFS also exposes an
Iceberg REST catalog, which Stage 1 may use.
